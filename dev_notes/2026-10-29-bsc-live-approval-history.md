# Fresh BSC approval discovery

Current scope: fetch the wallet address's transaction history from the existing explorer provider, independently of transactions stored on the phone. Validate each listed transaction and its on-chain receipt through the selected RPC, using an approval-only historical BSC reader if that provider returns a null receipt, derive owner-bound token/NFT approval targets from events, and verify the current allowance/operator/owner state before displaying a permission. Keep the existing signer and separate revocation transactions. Ethereum retains its direct log scanner, with fresh-history fallback after log failure.

Privacy: follow the existing optional Tor setting. With Tor off, requests use normal connectivity; the details page explains that providers receive the public wallet address and may see the IP. With Tor on, requests use the explicit local SOCKS proxy, require a connected Tor session and never fall back to direct connectivity. Account/provider/privacy-setting changes invalidate responses. Redirects and connection retries are disabled, history responses are size-bounded, and no request/body logging is added. The existing top-right details icon contains both privacy and history limitations, rather than displaying that text in the main scan list.

Discovery: reuse the existing BSC explorer endpoint and already-shipped release credential pool. Development uses that same pool for representative testing. Pin pagination to a block snapshot, preserve failed receipts for retry and distinguish discovery errors from current-permission failures. No new RPC endpoint, API key, provider purchase, wallet-history database query or signer is introduced. History discovery can miss relayed approvals and events outside the provider's listed transactions; manual checks remain available. Provider plans, quotas and availability still apply.

The user tested signed build 188 and reported failure. Its installed APK hash exactly matched the candidate, but its selected RPC was BlockRazor. A public old approval fixture reproduced the cause: BlockRazor and 48club returned null receipts, while the existing Binance source returned the correct receipt. Earlier build/credential parity did not account for different provider settings between installations.

The correction uses the selected RPC first. An explicit null BSC receipt may use the wallet's existing built-in Binance HTTP source for historical reads, without changing settings or forwarding custom-provider authentication. Verify the fallback chain ID and keep the original account, selected-source and optional-Tor guards. Validate receipt hash/block/owner/events before accepting targets or reusing the reader.
