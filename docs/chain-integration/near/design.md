# NEAR integration decisions

Scope: import the NEAR implementation from upstream Unstoppable Wallet 0.53.0 (`d6661c8d0dc02d259767f58b7cd73cabb877da18`), using NearKit `856d2e3148cad1b031cba9247ddcbda3f26382b8`. This is part of a local, unfinished Open Swap merge. The existing UI, direct providers, configured ratings, fees and signing controls must be preserved. New NEAR-only account/setup screens were approved by the user.

The closest analog is Stellar for named accounts and chain-native fungible tokens, with Solana as the reference for account-owned kit lifecycle and ambiguous broadcast handling. The import is existing upstream code; the differences below are assessed before publication, not treated as a new implementation already validated on a device.

## Delta decisions and checklist coverage

- **ADDR-1, ADDR-2, ADDR-3:** NEAR supports implicit hexadecimal account IDs and named accounts instead of Stellar's checksummed base32 addresses. Use the pinned SDK account-ID validator at send, watch, contacts and account-picker entry points. The local-backup entry path is under correctness review; validation cannot be inferred from the send screen. References: `NearChainPlugin`, `AddressHandlerNear`, `NearAddressValidator`, `AccountType.toNearWallet`, `AccountsStorage`.
- **ADDR-4:** Native NEAR transfers have no memo. NEP-141 token transfers may attach a public memo, capped at 256 bytes by the wallet. Do not reuse destination tags or silently attach a native memo. Reference: `NearChainPlugin.sendMemoSupport/sendTransactionData`.
- **AMT-1, AMT-2, AMT-3, AMT-4:** Use integer yoctoNEAR and integer token base units, with exact BigDecimal conversion. Native NEAR has 24 decimals; NEP-141 decimals come from metadata and must be bounded. NEP-141 transfers do not expose an ERC-20-style allowance or unlimited-approval value. References: `NearAmount`, `NearAdapter`, `NearTokenAdapter`, `AddNearTokenBlockchainService` and `NearTransactionConverter`. A fallback indexer balance must not be represented as a successfully verified contract balance; see SEC-3.
- **HIST-1, HIST-2, HIST-3:** One record summarizes net native/token movements for the account; multiple assets become a contract-call record. SDK transaction tags select wallets and filters. Do not count native value twice when receipts wrap or unwrap tokens. Reference: `NearTransactionConverter.netMoves/type`, `NearTransactionsAdapter` and SDK transaction conversion. Live history/filter parity is not yet exercised.
- **HIST-4, HIST-5:** Fee-only or action-only transactions appear as contract calls, with signer fees separate from transferred value. The current NEAR send bridge offers native/token transfers, not ERC-20 approvals. Imported arbitrary action history must never label a fee as a received transfer.
- **HIST-6, HIST-7:** A contract's symbol and token logs are untrusted. Preserve contract identity for unknown assets, do not let an alleged contact sender bypass unknown-token checks, and derive poisoning context from genuine outgoing transactions before applying the limit. Existing upstream code violates these decisions; SEC-1 and SEC-2 require disposition before publication.
- **TX-1, TX-2:** Confirmation binds destination, amount, memo, storage deposit and fee estimate. SDK rechecks full-access keys and recipient rules before signing. NEAR signs a recent block hash and access-key nonce rather than an EVM chain ID; the configured kit network and RPC provenance remain trust boundaries. References: `SendTransactionServiceNear`, SDK `TransactionSender.signWithHeight` and `NearKit.sendFt`.
- **TX-3:** Reserve native NEAR for prepaid gas, implicit-account creation and token receiver registration. Use `requiredNear`, not merely the charged gas estimate, for maximum sending. Reject unexpected registration-cost changes and excessive deposits. References: `BaseNearAdapter`, `NearAdapter`, `NearTokenAdapter`, `SendTransactionServiceNear` and SDK `FtActions/FeeCalculator`.
- **TX-4, TX-5, TX-6:** The SDK serializes sends under a mutex and saves pending records before broadcast. An ambiguous submission remains pending; explicit unknown-to-reached-nodes rejection can remove it. The wallet maps newly pending hashes back to a submitted result. Expiry and node-failure distinction must be retained; no funded timeout/retry has been exercised. References: SDK `TransactionSender`, `TransactionSyncer` and `SendTransactionServiceNear`.
- **TX-7:** Use exact integer conversion; validate account identifiers, contract identifiers, decimals, amounts and memo limits. Refuse limited-access keys for transfer signing. Arbitrary WalletConnect NEAR actions are not enabled by this import.
- **NET-1, NET-2, NET-3, NET-4:** Native RPC and optional indexer have different authority. SDK history has bounded pagination/backfill and rate-limit backoff; errors must remain distinct from zero balance or an empty successful history. The watched-token balance fallback violates that last requirement (SEC-3). Preserve visible sync failure and never equate a transport exception to on-chain rejection.
- **NET-5:** RPC selection uses built-in HTTPS sources; fallback ordering matches the pinned SDK. Account discovery/history use FastNEAR. Configure no borrowed API key. Inspect global Tor integration and actual traffic separately; ordinary OkHttp defaults are not packet-capture proof.
- **ACC-1:** Watch accounts map to `NearWallet.WatchOnly`; SDK `requireSigner` and access-key checks prevent signing. The backup restoration entry path still needs its own validation review.
- **ACC-2:** Export/restore the new watch type and account-scoped selected NEAR account ID. Cross-platform round-trip remains untested. References: `BackupProvider`, `AccountsStorage`, `RestoreSettingsService` and associated upstream tests.
- **ACC-3:** Kit/database identity includes app account ID, NEAR account ID and network. Release kit observers on account changes and delete chain storage through `clearAccountData`. The auto-enable collector's account binding is under correctness review; do not assume the active account and a delayed kit-start signal always match.
- **ACC-4:** Shared Swap, Private Send and CrossPay use the new provider preview/commit lifecycle. Keep the actual committed deposit target and amount, fresh fee validation, current local signer, PIN and account guards. Do not confuse a fee-estimation placeholder with a real deposit address.
- **ACC-5:** No new NEAR WalletConnect request handler is registered by this import. Unknown NEAR dApp action support must not be inferred from ordinary transfers.
- **PAR-1, PAR-2, PAR-3:** Seed derivation follows the pinned SDK's NEAR derivation. No iOS reviewer or paired runtime is connected to this task, so cross-platform address, backup and history parity are explicitly unverified. Do not send external handoff messages without the user's authorization.

## Publication status

The user chose to fix NEAR before publication. The original findings and wallet-layer repairs are dispositioned in review.md; test-vectors.md separates automated fixtures from unrun device, funded, Tor and iOS checks. No funded send, approval or bridge transaction is authorized or claimed as tested. The upstream merge is still local until build validation and publication complete.
